## Problem

Sonos sells good speakers and, since the May 2024 app rewrite, an app many owners
resent. The open source audio stack already solves synchronised playback, but only
for people willing to assemble it themselves. Two gaps are unserved:

1. Millions of people own hardware they like and an app they do not.
2. Every vendor walls its speakers off from every other vendor's speakers.

Neither gap needs new hardware to close.

## Chosen approach

Approach A staged into B.

- **Phase one (A):** a control app for speakers people already own. No firmware, no
  manufacturing, no inventory.
- **Phase two (B):** a flashable speaker operating system plus coordinator, so the
  same app also drives hardware the user owns outright.
- Custom manufactured hardware (Approach C) is a decision for after phase two, made
  with real users in hand.

Rejected at review time: Approach C first (cost before validation) and Approach D,
spec-first (Snapcast already occupies that space; a spec with one implementation is
a document nobody reads).

## Vision

### 10x check

The 1x product is a nicer Sonos remote. It is a skin on someone else's box and it
ends the day Sonos closes local control.

The 10x product is **one app that groups speakers across ecosystems and holds them
in sync**. A Sonos speaker, an AirPlay speaker and a Chromecast puck cannot play the
same song together today, because no vendor has a reason to make that work. It costs
roughly 2x a Sonos-only remote, incumbents cannot copy it without dismantling their
own lock-in, and it makes future first-party hardware just one more endpoint on a
network that already works.

The thesis in one line: **the boxes are fine, the walls are the problem.**

### Platonic ideal

A single binary that runs on a laptop, a Pi, a NAS, or nowhere at all. It finds every
audio endpoint in the house in under two seconds and shows them as rooms, not as
protocols. The user never learns the word "AirPlay". Grouping is drag and drop, and a
mixed-vendor group holds sync tight enough that walking between rooms sounds like one
system playing, with no slap echo and no audible correction. Note that "no phasing" is
not a promise anyone can keep: at 1 kHz, 17 cm of listener movement is half a cycle, so
room geometry produces phasing in overlap zones even with a perfectly synchronised
source. The objective is perceptual, and it is stated that way deliberately.
No account, no cloud, no telemetry. Every device gets a cryptographic
identity on first pair. Updates are signed and reversible. The whole configuration is
one readable file. When something sounds wrong, a diagnostics view shows live sync
offset and buffer health per room, so the answer is data rather than a forum thread.
The reference speaker is a published parts list and a printable case, so "this still
works in 2040" is verifiable rather than marketing.

### Design test

Every later decision is measured against one question: does it move toward "a
non-technical person sets this up in five minutes", or away from it?

## Scope, restructured after the outside voice review

The six accepted expansions above remain the vision and every one of them is still
wanted. They are no longer all in the first release. An independent review called the
original phase one "several mature projects stapled together", and that was correct.
Work is now staged behind a feasibility gate.

### M0. Feasibility spike, with a kill threshold written first

No architecture, no community, no interface. It answers one question: can endpoints
whose playout clock open-sonus cannot command be held in acoustic sync well enough to
sound right?

"Deliberately ugly" applies to the protocol drivers, not to the measurement harness.
The drivers are scaffolding. The harness produces the number the whole project turns on,
and it becomes the nightly CI rig later, so it is written and tested properly. See the
code disposal section.

Written in Python on top of existing libraries. No Rust in M0. The language decision
for the core is settled separately and must not be pre-committed by spike code.

M0 runs in three stages, cheapest kill first. Each stage can end the project, and
later stages are not built until earlier ones survive. The patent screen runs in
parallel throughout and depends on none of them.

```
  M0a  CONTROL AUTHORITY INVENTORY          desk + one speaker each, days
       |                                     KILL: no actuator finer than
       |                                     a coarse seek exists anywhere
       v
  M0b  CRUDE OPEN-LOOP RUN                  1 host, 2 speakers, 2 h + 2 h
       |                                     KILL: drift unarrestable, or
       |                                     correction is necessarily coarse
       v
  M0c  FULL RIG, 8 h, all required pairs    the published numbers
                                             KILL: decision table, below

  (parallel)  PATENT SCREEN                  no engineering dependency
```

#### M0a. Control authority inventory

Measurement does not create a controller. Before building any rig, establish what
each opaque endpoint actually lets you do. For Sonos, AirPlay and Cast, record:

- Seek granularity. Can you seek to a millisecond, or only to a second?
- Rate or pitch adjustment. Does any interface let you play slightly fast or slow?
- Buffer depth control, if any is exposed.
- Command latency distribution, not just its mean.
- Whether the receiver re-buffers or reseeks on its own initiative.
- Whether receiver output latency varies with volume, loudness processing, room
  correction or grouping state.

If no endpoint exposes an actuator finer than a coarse seek, there is no continuous
control loop to design and the cross-vendor claim dies here, before a microphone is
bought. Learning this during M0c instead costs the entire deadline.

#### M0b. Crude open-loop run

One host, two speakers of different brands, wired where the hardware allows, two
microphones on one shared converter. Two hours with no correction at all, to see how
fast offset walks away. Then two hours using the crudest correction M0a found.

This is the existential question in its smallest form: do two opaque ecosystems expose
enough effective control to arrest relative drift without objectionable discontinuities?
If offset walks away, or the only available corrections are coarse, or either receiver
re-buffers on its own schedule, stop.

#### M0c. The full rig

Only reached if M0a and M0b survive. This is where the loopback latency channel, the
streaming pipeline, the artefact classifier and the remaining endpoint pairs get built,
and where the eight-hour soak produces the published numbers. Eight hours is not
padding: it exposes thermal drift, periodic buffer management, lease renewal and Wi-Fi
events that two hours does not.

#### Decision table, committed before any code

The gate is not the threshold alone. It is the threshold plus the rules that stop a
marginal result being talked into a pass. The numeric criteria are committed below.
The fixed conditions are recorded once the endpoint set is bought, and no code runs
against this table until they are.

```
  NUMERIC CRITERIA
   N   max offset, 95th percentile, per pair    10 ms
   E   max single excursion                     30 ms
   R   max correction rate                       6 per hour
   M   max missing or low-confidence windows     1 %
   D   deadline, then decide regardless         90 days

  FIXED CONDITIONS, recorded in advance
   - required endpoint pairs, named by model and generation
   - firmware versions, pinned and logged
   - content corpus, fixed
   - network impairment profile, fixed
   - warm-up period, declared before the run

  EXCLUSION RULES
   - no dropping the worst pair
   - low-confidence windows are not excluded from the percentile; they
     count against M instead
   - no "the first hour was setup" unless the warm-up was declared up front
   - a firmware update mid-run voids the run; it does not excuse the data

  VERDICT
   Any required opaque-to-opaque pair failing any criterion by any amount
   kills the broad cross-vendor claim. No post-hoc threshold changes.
   Changing a number after seeing data means deleting the data and rerunning.
```

#### Where the numbers come from

Each number is set at the bar the product has to meet, not at the bar the hardware is
expected to reach. Setting them the other way round is how a gate becomes a formality.

**N, 10 ms.** Ten milliseconds is 3.4 m of air, which is inside the path length
difference a listener already accepts between two speakers in one room. Hold the
sync error at the same order as the geometry the room imposes anyway and a mixed
group sounds like one system. This is a 95th percentile over roughly 28,800 windows,
so it describes the normal state of the run rather than its best moment.

**E, 30 ms.** The tail that a percentile does not cover. E is three times N and stays
inside the fusion range for music, where the echo threshold sits nearer 50 ms. The
margin is deliberate, because echo thresholds are measured on clean single reflections
and a real excursion arrives with a correction artefact attached to it. E is a ceiling
on the single worst window in the whole run.

**R, 6 per hour.** A group that holds sync by resyncing every ninety seconds is inside
the offset budget and not shippable, so correction frequency is a first-class result
rather than a note. Six per hour is one correction every ten minutes, or two to three
across an album. R counts every correction a driver issues, taken from the driver logs,
so the verdict stays machine-readable.

**M, 1%.** M has to sit an order of magnitude below the 5% tail that N is measured on,
or lost coverage alone can move the verdict. At 1%, even if every missing window hid a
worse offset than every measured one, the true 95th percentile moves to about the 94th
of the measured series and the verdict does not change. At 5% the percentile carries no
information at all. 1% of an eight-hour run is about five minutes, which is a fair
allowance for quiet passages and buffer events.

**D, 90 days,** counted from the first M0 commit. It covers the staged plan with room
for reruns: about a week for M0a, three weeks for the harness core and its synthetic
suite, a week for M0b, and four weeks for the rig, the remaining pairs and the soaks.
Hardware procurement is inside the clock rather than beside it, because a clock that
starts after the parts arrive is a clock you can move. D is what stops the rig becoming
the project. If the required pairs have no admissible eight-hour data on day 90, the
verdict is fail, and fail routes to the fallback product rather than to an extension.

#### M0a partial result: Sonos control authority, 2026-08-11

Established against the Playroom Play:3 and its group coordinator without playing any
audio. Every row below came from the device's own service description or from read-only
queries.

| Question | Answer | Source |
|----------|--------|--------|
| Rate or pitch adjustment | **None.** `TransportPlaySpeed` allows only `1`, and `Play` at 1.02 and 0.98 is refused with UPnP error 717 | SCPD, then live |
| Seek modes | `TRACK_NR`, `REL_TIME`, `TIME_DELTA`, and `X_DLNA_SeekTime` | SCPD, `GetCurrentTransportActions` |
| Seek granularity | **1 s.** A fractional `REL_TIME` is accepted without error and the fraction is silently discarded | Origin byte offsets |

**How seek granularity was measured, without a microphone.** open-sonus served the
speaker a 300 s constant-rate PCM file over HTTP, so a byte offset maps exactly to a time.
The speaker then declares its own seek resolution by which byte it asks for. Every
fractional target came back on a whole second.

| Seek requested | Byte fetched | Equals | Fraction |
|----------------|--------------|--------|----------|
| `00:00:30`     | 5292044      | 30.000000 s  | — |
| `00:01:30.500` | 15876044     | 90.000000 s  | discarded |
| `00:02:30.250` | 26460044     | 150.000000 s | discarded |
| `00:03:30.125` | 37044044     | 210.000000 s | discarded |
| `00:04:20.750` | 45864044     | 260.000000 s | discarded |

This technique is worth keeping. It costs nothing, it needs no rig, and it gives an exact
answer, so it should run against every pull-side endpoint before the microphones arrive.

Note the failure style. Sonos does not reject a sub-second seek. It accepts it, returns
success, and throws the fraction away. Anything that trusts the return value believes it
holds an actuator 100 times finer than the one it has.

Four consequences, and the first one decides how to read the M0a kill criterion.

**There is no in-band rate actuator, so the actuator has to be the origin.** A Sonos in a
bridged group fetches from open-sonus, so the fine control is not seek at all. It is the
byte stream served: resample slightly, or insert and drop samples. That is a continuous
rate actuator applied outside the device. So "no actuator finer than a coarse seek" is
true of the Sonos control API and false of the bridged data path, and the kill criterion
has to be read against the path that will actually carry audio. Seek stays as the coarse
actuator, for initial alignment and for recovery from a large excursion.

**Per-endpoint rate control forces per-endpoint streams.** If the actuator is the served
stream, then two Sonos units fetching one URL share one actuator and cannot be corrected
independently. Section 7 asks for one encode per output format. Independent correction
asks for one stream per endpoint. The pull side cannot have both. This answers the matrix
row the plan left open: on the pull side, either pay for per-endpoint encoding, or give up
per-endpoint correction.

**Seek is not a correction, it is a restart.** Each seek tore down the connection, re-read
the file from byte 0, and opened a new range request. So the coarse actuator is not merely
coarse at 1 s against an N of 10 ms, it also interrupts the stream every time it is used.
That makes it usable for initial alignment and for recovery from a large excursion, and
unusable as a routine corrector at any rate R would permit.

**Budget against the latency tail, not the mean.** The coordinator's p95 of 1021 ms
against a p50 of 20 ms is two orders of magnitude above N. A loop tuned on the 88 ms mean
is tuned on a number the device almost never produces. This is the case the inventory
asked for when it said distribution rather than mean, and it appeared on the first
device measured.

**Fallback if the gate fails.** The project repositions to control plus first-party and
Snapcast endpoints, and the cross-vendor claim is dropped rather than quietly weakened.
That fallback is a real product. The gate only has value if it can actually route you
there. A negative result here is a cheap success.

#### The rig

One multi-channel audio interface, one measurement microphone per speaker, plus a
loopback channel fed from the host's own output. Every channel shares one converter
clock, so the instrument has no internal drift to confuse with the signal.

```
  host (open-sonus)
    |  |
    |  +--- loopback cable ------------+
    |                                  |
    +--> speaker A  ~))  mic1 ---------+
    +--> speaker B  ~))  mic2 ---------+
    +--> speaker C  ~))  mic3 ---------+
                                       |
                      +----------------v----+
                      | multi-channel iface |
                      | ONE converter clock |
                      +----------+----------+
                                 |
                     streaming rolling correlation

  loopback vs mic  = absolute tap-to-sound latency
  mic vs mic       = relative room drift
```

Two independent USB microphones would have two independent sample clocks drifting
against each other at rates comparable to the thing being measured. That rig measures
itself. One converter, always.

Speaker distances are measured once and subtracted at roughly 2.9 ms per metre. Treat
that as a coarse correction, not a precision one: microphone position, acoustic centre
uncertainty, reflections and room temperature all matter more than the nominal
propagation figure. Do not quote a result to a precision the placement does not support.

#### Test content

Representative music with a short broadband probe burst embedded every few seconds. The
probe has a single sharp autocorrelation peak and no periodic ambiguity, and offset is
read from probe returns. Music fills the gaps so endpoints see normal program material
and exercise their real codec, DSP and buffer behaviour.

Music alone is not safe to measure against. Real music has repeated beats, sustained
tones and reverb tails, and rolling correlation can jump by exactly one beat and hold
there. A smooth continuity prior then produces a tight, confident, wrong percentile
series across thousands of windows. A probe with one autocorrelation peak removes that
failure mode; estimator hardening on music alone cannot, because there is no ground
truth to validate the hardening against.

#### Earning the right to trust the number

Two stages, both before any opaque endpoint is measured.

1. **Synthetic.** Signals with known injected offsets: 0, 1, 5, 20, 100 and 500 ms,
   negative offsets where B leads A, a drift from 0 to 50 ms over a simulated run, low
   signal-to-noise ratios, a silent window, and a periodic loop as a false-peak trap.
   The harness must recover the offset or report low confidence and refuse to produce a
   number. Never a plausible wrong number.
2. **Live control.** A Snapcast-only pair, which is sub-millisecond by design. If the
   rig cannot show Snapcast as tight, the rig is broken. This is necessary, not
   sufficient: it validates one signal path, not the estimator across its whole range.
   That is what stage one is for.

**Blind validation.** An operator injects undocumented step changes into the timeline.
If the pipeline misses any blind step, no endpoint result from that run is admissible.

#### Artefact detection

Drivers log every correction they issue. The harness scans the recording for candidate
mutes, gaps and pitch shifts, and dumps a short clip around each event.

These detectors produce triggers, not evidence. A level floor does not prove a mute,
and a confidence collapse does not prove a gap; quiet program material and simple
decorrelation produce both. The clip is the evidence and a human confirms it.

**The listening is blinded.** The confirmer does not know which clips sit on correction
events and which are random controls. Otherwise the test measures expectation.

#### Capture pipeline

Streaming, not record-then-analyse. Eight hours of four channels at 48 kHz and 24 bits
is 16.6 GB, and a sampler that wakes every few minutes cannot see a 200 ms correction
event anyway.

```
  interface (shared clock)
        |
        v
  ring buffer, ~60 s
        |
        +--> rolling correlation, 1 s hop      -> offsets time series
        |                                          t, pair, offset, confidence
        +--> artefact detector -> 10 s clips
        |
        +--> raw multichannel archive
```

Percentiles are computed over every window, roughly 28,800 per eight-hour run, not over
a handful of samples.

Raw multichannel audio is retained for every run until the estimator is trusted. An
estimator defect found later destroys evidence that cannot be recovered, and rerunning
an eight-hour soak is expensive. Once the estimator is trusted, repeat and nightly runs
keep the offsets series and clips only.

#### Code disposal

```
  spike/
  ├── drivers/       throwaway. ugly is fine, no tests
  └── harness/       written to keep. tested. becomes the nightly CI rig
```

The harness survives because the plan already needs a nightly acoustic rig in CI, and
building it twice is waste. The drivers do not survive, but they are not deleted either:
they may embody the only discovered control semantics, and git keeps them regardless, so

### M1. Narrow first release

Only after M0 passes. One host platform, one interface, one source type, two endpoint

Three things stay in M1 despite the cut, because they are cheap now and expensive

## Grouping model (resolves decisions 1 and 3)

Two grouping modes exist, and the interface always shows which one is active.

**Native group.** Speakers of one brand are grouped using that brand's own mechanism.
The vendor coordinates internally, so sync is as tight as the vendor can manage, and
the vendor plays its own licensed stream. Spotify, Apple Music and Tidal work here,
because open-sonus never touches the audio.

**Bridged group.** Speakers of different brands are grouped with open-sonus as the
audio source. A native group can be nested inside a bridged group and treated as one
endpoint. Sources are limited to audio open-sonus is entitled to hold: local files,
Jellyfin, Navidrome, Subsonic, internet radio, and line-in.

A bridged group is **not** a uniform push fan-out, and describing it as one hides the
component that matters. AirPlay and Snapcast receive pushed, timestamped audio. A Cast
receiver is handed a media URL and fetches it. A Sonos speaker in bridged mode is given
`SetAVTransportURI` and also fetches. So two of the four transports pull, which makes a
local stream origin a first-class component with its own failure surface and its own
security boundary, not an implementation detail inside two drivers.

**Bridged commercial audio has one candidate route, and it is unverified.** The user
starts playback in the Spotify or Apple Music app on their own phone and sends it to
open-sonus as an AirPlay target. Two corrections to an earlier, wrong description of
this:

- AirPlay carries an encrypted, encoded, timed stream. The phone does not hand over
  decoded audio. Receiving it means implementing an unofficial AirPlay receiver, which
  is not Apple-licensed and which Apple can break.
- Cast is not an equivalent ingress. A Cast receiver is normally instructed to fetch
  media itself rather than being pushed a stream, so "cast it to us" does not work the
  same way and may not work at all.

The legal position is also not settled by the absence of a reimplemented service
protocol. Copyright, digital rights management, terms of service and Apple licensing
questions all remain open. Treat this route as a feasibility and legal question to be
answered by the spike, not as a designed feature.

What is not possible and must never be implied: open-sonus pulling a commercial
stream itself and fanning it out across brands.

```
  NATIVE GROUP                     BRIDGED GROUP
  (one brand, vendor coordinates)  (mixed brands, open-sonus is the source)

  Spotify -> Sonos coordinator     local / Jellyfin / radio / line-in
                |                  or phone -> AirPlay in (unverified)
```

**Origin outage is its own failure mode.** If the host changes IP on a Wi-Fi roam,
sleeps, or loses its port binding, every pull endpoint drops at once while every push
endpoint keeps playing. That is not drift, so drift eviction does not cover it. It
needs its own detection and its own policy, in section 2.

## Delivery model

Open community from day one. The repository is a product surface from the first
commit, not after the code is good. Three consequences that bind the architecture:

1. **Work must be parcelable.** Every module needs a written interface contract
   before it has contributors, or parallel work produces merge pain instead of
   progress. The endpoint abstraction, the sync library and the four surfaces are the
   natural seams.
2. **Contributor throughput is negative at first.** Review, triage and onboarding are
   real costs paid before anyone becomes productive. Budget for them explicitly
   rather than treating them as overhead.
3. **Governance is scope.** Licence, contribution guide, code of conduct, decision
   process and security disclosure policy are phase one deliverables, not paperwork
   to add later.

Milestones are sliced so each one ships something usable on its own, and so a
newcomer can pick up a whole milestone without needing the rest in their head.

## Licensing

**Apache-2.0** for the software, chosen for adoption and for its explicit patent
grant. Hardware designs default to CERN-OHL-P to match, unless deliberately revisited.

This is the least reversible decision in the plan. Once outside contributors have
merged code, relicensing requires their unanimous agreement.

Two consequences accepted with it:

1. **The mission is not protected by law.** A manufacturer may take this code, close
   it, and ship the kind of locked-down product the project exists to oppose. The
   defences are trademark policy, the gravity of the reference implementation, and a
   published specification later. None of them are enforcement. Decide the trademark
   policy early, because it becomes the only lever.
2. **GPL dependencies must stay behind process boundaries.** Snapcast and Lyrion are
   GPL. Stated precisely: Apache-2.0 code may be incorporated into a GPLv3 work, but
   not the reverse, and the obligations attach when a combined work is distributed. So
   a distributed Apache-licensed binary must not link GPL libraries. Process separation
   substantially reduces the risk but is not an automatic safe harbour, because closely
   coupled processes can still be argued to form a combined work. This needs an actual
   legal review before Snapcast ships in anything, not a rule of thumb, and a
   continuous integration check that fails when a GPL library enters the dependency
   graph.

Licence audit of the likely dependency set is a phase one task. Confirm each one
before use rather than trusting this list:

| Component | Expected licence | Use as |
|-----------|------------------|--------|
| Snapcast | GPL-3.0 | Separate process only |
| Lyrion Music Server | GPL | Separate process only |
| SoCo, node-sonos | MIT | Library, safe |
| pychromecast | MIT | Library, safe |
| shairport-sync | Permissive, verify | Separate process, safer regardless |
| AirPlay **sender** | UNKNOWN, verify in M0 | Separate process. See below |
| Music Assistant | Apache-2.0 | Library or process, safe |

**The AirPlay sender is a real gap, not a footnote.** shairport-sync is a receiver.
A bridged group needs open-sonus to be a sender to somebody else's AirPlay speaker,
and nothing in this plan provided one. The decision is to adopt an existing sender
behind a process boundary and verify its licence during M0, because writing an AirPlay 2
sender is the single largest engineering item in the project and putting it inside a
cheap spike would make a negative M0 result unattributable: protocol, or our code?

The mature senders come from the GPL family. If that holds after the audit, the process
boundary is permanent and the CI dependency check must cover it. Either way, Apple can
break the protocol, and that risk is identical whether the code is ours or borrowed.

## Technical foundations

- **Core:** Rust. Audio path, sync engine, endpoint drivers. Two earlier justifications
  do not hold up. Avoiding garbage collector pauses is weaker than it sounds: scheduling,
  allocation discipline and the operating system's audio interfaces determine real-time
  behaviour far more than the language does, and no language rescues an endpoint whose
  clock you cannot command. Mobile embedding is a real requirement but it lands in M2,
  while the two-language cost lands in M1, so it cannot carry the decision on its own.
  What the decision actually stands on: this is a reversibility-2 choice, and swapping
  the core language after contributors have merged is close to impossible, so choosing
  late is not cheaper; the audio path holds and timestamps buffers on a Pi-class
  processor, where predictable memory behaviour still matters; and a single static
  binary with no runtime matches the distribution list exactly.
  **Cost accepted in writing:** M1 pays for two toolchains, two CI lanes and a
  core-to-surface boundary to serve ten households. That is deliberate, not incidental.
- **Surfaces:** TypeScript. App, local browser page, diagnostics view. The command
  line tool wraps the same local API.
- **Contract:** a documented local API is the only thing between core and surfaces.
  Every surface is a client of it, including the first-party app. If a surface needs a
  private channel into the core, the API is wrong.
- **Repository:** monorepo, with the endpoint abstraction, the sync library and each
  surface as separately ownable packages. Community work is parcelled along those
  seams.
- **Server question, answered:** bridged groups need a host process, because something
  must hold and timestamp the audio. Native groups do not. "No server required" is
  therefore true only for native groups and the onboarding copy must say so rather
  than discover it for the user.
- **GPL rule:** Snapcast and any other GPL component runs as a separate process behind
  a protocol. Never linked. Enforced by a dependency check in continuous integration.

## M1 is done when

M1 is the narrow first release, not all of phase one. Its exit criteria are short on
purpose. Meeting the phase one criteria below is what M2 and beyond are for.

1. Ten households run a mixed-vendor bridged group for eight hours without a support
   request.
2. Measured acoustic drift stays inside the budget M0 established, verified by the
   nightly rig against the release tag.
3. No control command is accepted from an unpaired client.
4. All six diagnostic signals are visible per room: sync offset, buffer health, signal
   strength, event subscription delivery health, host clock sanity, processor headroom.
5. Two protocols are implemented and the endpoint contract is frozen against both.

## Phase one is done when

1. A fresh user with two speakers of different brands reaches synchronised audio in
   under five minutes, with no terminal and no config file.
2. Discovery of all reachable endpoints completes in under two seconds on a typical
   home network.
3. Measured acoustic drift inside a same-protocol group stays under the published
   budget, and the cross-vendor budget is published as a measured number rather than
   a claim, whatever that number turns out to be.
4. Tap-to-sound latency is measured and published per protocol. The 200 ms target
   applies to protocols where open-sonus controls playout. Buffered protocols such as
   AirPlay and Cast impose their own latency that keeping endpoints warm does not
   remove, so a single cross-protocol target would be a claim the physics does not
   support.
5. No control command is accepted from an unpaired client.
6. The reference node build has been reproduced from the written instructions by
   somebody who did not write them.

## Review decisions

### Section 1: architecture

- **State reconciliation.** open-sonus is never the only writer of speaker state.
  Subscribe to vendor events where they exist, back them with a low-frequency poll,
  renew subscriptions aggressively, and give the interface an explicit stale state
  showing the last confirmed reading and its age. Never display a confident guess.
  This is a direct answer to the defect that made the incumbent app hated.
- **Discovery failure is a designed feature, not an edge case.** Probe every network
  interface, detect dropped multicast, offer direct address entry and subnet scan as
  first-class paths, and make the empty state name the likely cause with a next step.
- **Host loss in bridged groups.** Warn once when a bridged group is created on a host
  that can sleep. On host loss, stop endpoints cleanly rather than letting buffers
  trail off, and resume at the correct position when the host returns. Host failover
  to another node is deferred, not rejected.

### Section 2: errors and rescue

- **Two failures produce no error object at all:** dropped multicast discovery and a
  lapsed event subscription. Both need active liveness checks, not error handling.
- **Config writes are atomic and keep the previous version.** A power cut during a
  write is the one failure that makes the product unbootable.
- **Provider plugins run as separate processes** over a documented protocol. A plugin
  can never stall the audio thread, and plugin authors use any language they like,
  which matters more than performance for a community-first project.
- **Drift policy.** An endpoint exceeding the drift budget for a set period is muted
  and removed from the group, with the room and the reason shown, and rejoined
  automatically once it holds sync. Hysteresis is required so a marginal endpoint does
  not oscillate.
- **Origin outage policy.** Distinct from drift and needing its own owner. When the
  host changes address, sleeps or loses its port binding, every pull endpoint fails at
  once while push endpoints continue, which sounds to the user like half the house
  stopping for no reason. Detect it at the origin, not per driver: an origin that loses
  all its readers simultaneously is an origin problem. Stop the push side cleanly rather
  than letting it play on alone, name the cause in the interface, and resume at the
  correct position when the origin is reachable again. Bind to a stable address where
  the platform allows it, and treat a host address change as an event worth warning
  about before a group is created, alongside the existing sleep warning.

### Section 3: security

Rules, no alternatives considered:

1. The local API validates Host and Origin headers and requires a token on every
   request. A page served on localhost is reachable from any website the user visits
   via DNS rebinding, and cross-origin rules alone do not prevent it.
2. Dependency auditing runs in continuous integration and fails the build.
3. Pairing uses trust-on-first-use with a visible fingerprint and a short code shown
   by the core.
4. The security limit is published: below the local API, vendor devices accept
   unauthenticated commands, and open-sonus cannot change that.

Decided:

- **Release signing is keyless**, using short-lived build-time credentials tied to the
  repository identity, with every signature written to a public transparency log.
  Reproducible builds are a goal so third parties can verify artefacts. No human holds
  a long-lived signing secret.

### Section 4: data flow and interactions

- **Optimistic for the user's own actions, never for observed state.** Controls respond
  instantly to commands the user just issued and reconcile on confirmation, snapping
  back with a reason if the device disagrees. State that changed elsewhere is never
  predicted. This resolves the tension between the 200 ms target and the honesty rule.
- Group creation is not one operation. A group forms with whichever members joined,
  and any member that failed is named with a retry.
- Commands are idempotent by group generation id. Volume drags coalesce to the last
  value and are rate-limited per endpoint.

### Section 5: code quality

- Shared retry, polling, capability negotiation, latency estimation, **discovery and
  the stream origin** live above the drivers. A retry loop inside a driver means the
  abstraction has leaked, and the same argument applies to a stream server inside a
  driver. Discovery is on this list for a harder reason than tidiness: three drivers
  each opening their own mDNS browser is three processes contending for port 5353 on
  one host. That is a bind conflict, not a style preference. One discovery service,
  one origin.
- Do not add a second plugin system. The provider boundary is the only one until
  something outside the repository needs another.
- Per-endpoint latency is a measured, updating estimate from the start. A fixed
  per-protocol constant will be wrong and replacing it later means rewriting fan-out.
- The group manager is where complexity concentrates: two modes, partial membership,
  drift eviction, and reconciliation against external writers. Two reviewers on it.
- **Interface timing.** Implement Sonos and one genuinely different protocol first.
  The differences between them define the endpoint contract. Only then publish it as
  stable, with a versioning policy, and open it to contributors.

### Section 6: tests

- Protocol drivers are tested against recorded transcripts captured from real devices.
- The shipping-confidence test is an eight-hour soak of a mixed-vendor bridged group
  with acoustic drift sampled throughout. Initial alignment is easy; drift over hours
  is what actually fails and no short test catches it.
- A deliberately hostile reference plugin, which hangs, crashes and floods, is part of
  the test suite.
- **The acoustic rig never executes untrusted code.** Pull requests from forks run only
  hosted unit and simulated tests. The rig runs nightly against the main branch, and on
  demand for a maintainer who has read the change. The runner sits on an isolated
  network segment with no route to the rest of the house.

### Section 7: performance

- Poll rate is adaptive: fast for endpoints in an active group, slow for idle ones.
- Encode once per output format, not once per endpoint. Resample in the same place.
  This is straightforward on the push side. On the pull side it collides with sync:
  two Cast devices fetch the origin independently and each lands wherever the stream is
  when it connects, so sharing one encode means sharing one live edge, and joining a
  live edge at different moments is the sync problem one layer down. Not resolvable on
  paper. It is a row in the M0 authority matrix.
- The whole bridged path is budgeted against a Pi-class processor, not a laptop.
- Discovery never blocks the interface and streams results in.
- Hitting 200 ms tap-to-sound on an idle group needs endpoints kept warm. Accepted
  trade: a little power and network for how the product feels. This buys nothing on the
  pull side: a Cast receiver held warm is an open session the device may time out on its
  own schedule. Consistent with the target only applying where open-sonus controls
  playout, but say so rather than implying the trade helps everywhere.

### Section 8: observability

- Local structured logs with rotation. A support bundle command that redacts network
  names, addresses and tokens before a user posts it. An optional local metrics
  endpoint for self-hosters.
- **No automatic data collection of any kind.** The software never transmits anything
  on its own. Diagnostics are produced on request, readable by the user, and attached
  to an issue only by their choice. The promise stays one sentence with no exceptions.

### Section 9: deployment

- **One core, two build shapes.** The same Rust crate builds as a background service
  and as an embedded library inside the mobile and desktop apps. The app alone handles
  native groups with no setup at all. Bridged groups additionally need a host.
  Because hosting a bridged group from a phone is deferred as probably infeasible, the
  embedded build is permanently native-only. That is a capability tier, and **the local
  API must advertise it**, or an app will offer a bridged group it cannot host.
- The local API negotiates versions in both directions, because app store review
  guarantees the app and core will be at different versions on real machines. This is
  an M2 requirement, not an M1 one: at M1 the core and its single surface ship together.
  Carry the version field from the first release so the negotiation has something to
  negotiate over, and defer the protocol itself.
- Config schema is additive only, carries a version field, and preserves unknown keys.
  This is what makes rollback by reinstalling the previous version actually work.
- Distribution: core through Homebrew, deb, Docker and a Home Assistant add-on. Apps
  through app stores, F-Droid and direct download. The browser page is served by the
  core and needs no distribution.
- Post-release verification is the nightly rig run against the release tag, with the
  measured drift number published per release.

### Section 10: trajectory

Reversibility, where 1 is effectively permanent and 5 is easily changed:

| Decision | Reversibility |
|----------|---------------|
| Apache-2.0 licence | 1 |
| Community from day one | 2 |
| Rust core | 2 |
| Embedded core in the app | 3 |
| Plugin process model | 3 |
| Endpoint interface contract | 3 |
| Keyless signing | 4 |
| Control-only streaming | 4 |

Chosen debt: two languages, two build shapes, GPL process boundaries to police, and a
physical test rig that needs a room and attention.

The one-year question: if Sonos closes local control in month eight, AirPlay,
Chromecast, UPnP, Snapcast and the reference node all keep working. The project
survives with a dented feature list. That is the return on the cross-vendor decision.

### Section 11: design and UX

- Every required interface state already has an owner: empty is the discovery failure
  design, partial is the partial group, error is drift eviction, loading is the
  reconciler's stale indicator.
- **Grouping across brands always succeeds.** When a source cannot be held by a bridged
  group, the interface offers the phone route as a one-tap action rather than blocking
  or warning. Plain language only. Protocol names never appear in the interface.
- Named slop risk: a grid of gradient cards with emoji section headers. It looks like
  every generated dashboard and nothing like a physical audio product.
- Run /plan-design-review on this plan before implementation.

## Open risks carried into the review sections

1. Sonos can restrict or remove local UPnP control at any time. Sonos's own supported
   developer interface is cloud-routed; local UPnP control exists in the products but
   is unofficial and incomplete. It must be treated as an unstable dependency, never as
   a platform contract. Mitigated but not removed by decision 1.
2. **Cross-vendor sync accuracy is unproven, and the doubt is stronger than first
   written.** Snapcast achieves its figures precisely because its own client controls
   timed playout and clock correction. That result does not transfer to an endpoint
   whose buffering, resampling and playout clock you cannot command. A measured,
   updating per-endpoint latency estimate cannot compensate for an endpoint that does
   not obey, unless the system has continuous acoustic feedback from every room, which
   is not a product anybody will install. Each protocol grants radically different
   authority over time: Snapcast full, AirPlay source-timestamped, Cast fetch-and-
   buffer, Sonos transport commands only. This is the assumption the whole cross-vendor
   thesis rests on, and it is currently unvalidated.
2b. Control plane and data plane grouping tension. RESOLVED, see the grouping model
   below.
3. Pairing friction fights the five-minute setup goal. Decisions 4 and the design
   test are in direct tension and need an explicit resolution.
4. "Open hardware" as a parts list will disappoint some readers who expect something
   purchasable. Needs careful wording from the first commit.
5. **Control authority may not exist at all.** Distinct from risk 2, which is about
   accuracy. This one is about whether there is anything to control. If Sonos and Cast
   expose only coarse seeks, no control loop can be designed at any accuracy. M0a
   answers it first because it is the cheapest question in the plan.
6. **Receiver output latency may not be a constant to estimate.** It can vary with
   volume, loudness processing, room correction and grouping state. A per-endpoint
   latency estimate that assumes a slowly-varying quantity will chase a value that
   steps when the user turns a knob.

The inventory lane was expected to be documentation only. It is not: reading seek
resolution off the control API gives the wrong answer, so the lane needs a served stream
and a request log to read the answer off the receiver's behaviour instead. That code is
written and tested, and it arrived before the capture lane because it needs no rig.

**Lanes**

```
  LANE 1  documentation      M0a inventory -> feeds every driver lane
  LANE 2  documentation      patent screen (fully independent, whole of M0)
  LANE 3  harness core       capture | correlate + synthetic | content
  LANE 4  harness analysis   artefacts, report        (waits on correlate)
  LANE 5  drivers            snapcast now; sonos/cast/airplay after M0a
```

**Execution order.** Lanes 1, 2, 3 and the Snapcast driver start immediately and in
parallel. Lane 4 starts when correlate lands. Lane 5's opaque-endpoint drivers start
when M0a reports. M0b is a join point: nothing downstream of it begins until it passes.

**Conflict flags.** Lane 4 imports from `spike/harness/correlate`, which lane 3 owns and
is actively changing. Freeze the correlate interface before lane 4 starts, or accept the
merge pain. No other two lanes touch the same directory.
